# Vector Clocks

> **A logical clock that captures causal ordering in distributed systems — detects concurrent versus happened-before relationships without relying on synchronized physical clocks.**

## The Problem It Solves

You're an engineer on Amazon DynamoDB's replication team. A customer in Tokyo updates their shopping cart, and milliseconds later, the same customer (on a different device sync'd to the same account) adds another item. These two writes hit different replicas — Tokyo and Virginia — simultaneously. When the replicas eventually reconcile, how do you know whether one write supersedes the other, or whether they're independent concurrent operations that must be merged? Physical timestamps won't help — clock skew between data centers can be hundreds of milliseconds, and NTP can drift. Lamport's scalar clocks tell you that event B happened after some event A, but they can't tell you that two events are *concurrent* — that neither happened-before the other.

This is the causal ordering problem. Vector clocks solve it by giving each node its own integer counter that ticks forward on every local event. When nodes communicate, they merge their clocks by taking the element-wise maximum. The resulting vector captures the *happens-before* partial order: you can determine whether event A causally precedes event B, whether B precedes A, or whether they're concurrent (unrelated).

The practical value is immense. In Dynamo, when two concurrent writes to the same key are detected, the system returns both versions to the client for reconciliation. In Riak, the vector clock (called a "causal context") is attached to every value so siblings can be identified and resolved. In CockroachDB, vector clocks track causal dependencies between transactions to enforce serializable isolation. Without vector clocks, every concurrent update would silently overwrite the other — data loss at scale.

## Architecture & Internals

```
┌───────────────────────────────────────────────────────────┐
│                    Vector Clock Semantics                  │
│                                                           │
│  VectorClock { "A": 3, "B": 1, "C": 2 }                  │
│                                                           │
│  ┌─────┬─────┬─────┬──────────────────────┐              │
│  │     │  A  │  B  │  C                   │              │
│  ├─────┼─────┼─────┼──────────────────────┤              │
│  │ VC₁ │  1  │  0  │  0    (A's local tick)│              │
│  │ VC₂ │  1  │  1  │  0    (B's local tick)│              │
│  │ VC₃ │  2  │  1  │  0    (A ticks again)│              │
│  │ VC₄ │  2  │  1  │  1    (C ticks)      │              │
│  └─────┴─────┴─────┴──────────────────────┘              │
│                                                           │
│  COMPARISON RULES:                                        │
│                                                           │
│  VC₁.Compare(VC₃) = "before"     [1,0,0] < [2,1,0]      │
│  VC₁.Compare(VC₂) = "concurrent" [1,0,0] ‖ [1,1,0]      │
│  VC₃.Compare(VC₄) = "before"     [2,1,0] < [2,1,1]      │
│  VC₃.Compare(VC₃) = "equal"      [2,1,0] = [2,1,0]      │
│                                                           │
│  MERGE (element-wise max):                                │
│  Merge([3,0,1], [1,5,2]) = [3,5,2]                       │
│                                                           │
│  TICK (local event):                                      │
│  Tick("A") on [3,0,1] = [4,0,1]                          │
└───────────────────────────────────────────────────────────┘
```

A `VectorClock` (`main.go:14`) is simply `map[string]int` — a mapping from node identifiers to logical tick counters. This sparse representation means we only store entries for nodes that have generated events, which is memory-efficient in large clusters where any given clock might touch only a subset of nodes.

**On `Tick(node)`** (`main.go:26-29`): Increments the counter for the given node by 1. Called before every local event on that node. This is how the clock moves forward — each node's counter is a logical timestamp representing "number of events generated by this node."

**On `Merge(other)`** (`main.go:34-42`): Takes the element-wise maximum for each node present in either clock. This is the critical operation that captures causality. When node A receives a message from node B that includes B's vector clock, A merges B's clock into its own and then ticks its own counter. The result is that A's clock now reflects all events that B has seen *plus* the new event on A.

**On `Compare(other)`** (`main.go:48-76`): Examines all nodes present in either clock. If for every node, this clock's value ≤ the other's, then this clock "happened-before" the other. If for every node, this clock's value ≥ the other's, then this clock "happened-after" the other. If some values are greater and some are less (mixed), the clocks are "concurrent" — neither happened-before the other. Both equal in all positions means "equal."

## Production Use Cases

- **Amazon Dynamo** — Dynamo attaches a vector clock to every stored value. On read, if the coordinator receives multiple versions with concurrent vector clocks, it returns all versions to the client. The client (or application-level resolver) reconciles them, and the reconciled version is written back with an updated vector clock.
- **Riak** — Basho's Riak KV uses a variant called "dotted version vectors" (a vector clock + per-replica dot) as the causal context for every object. This enables automatic sibling detection and the famous "Riak allows siblings" behavior — concurrent writes are preserved, not silently overwritten.
- **Cassandra lightweight transactions** — Cassandra's Paxos-based LWT uses vector clocks (in the form of ballot numbers + timestamps) to determine the ordering of conditional updates for Compare-And-Set operations.
- **CockroachDB** — CockroachDB uses hybrid logical clocks (HLCs), which combine physical time with logical counters, as the basis for its transaction timestamps. HLCs provide both causal ordering (from the logical counter) and real-time bounds (from the physical component).
- **Apple's FoundationDB** — FoundationDB uses version stamps (monotonically increasing integers per transaction) that serve a similar purpose to vector clocks for detecting conflicts in their optimistic concurrency control.

## When to Use It

| Scenario | Use Vector Clocks? |
|----------|-------------------|
| You need to detect concurrent writes across replicas | **Yes** |
| You need to preserve causal ordering in an eventually consistent system | **Yes** |
| You're building a multi-master replication system | **Yes** |
| Your system has a small, fixed number of nodes (≤ 100) | **Yes** |
| You need a globally unique total order of all events | **No** — use a centralized sequencer or TrueTime |
| Your system has thousands of nodes (clock size grows with node count) | **No** — consider interval tree clocks or dotted version vectors |
| You only need happened-before detection for a single process | **No** — Lamport scalar clocks are simpler and sufficient |

**Alternatives**: **Lamport scalar clocks** provide happens-before detection but cannot detect concurrency — event A having a lower counter than B doesn't guarantee A happened before B, only that B didn't happen before A. **Version vectors** are functionally identical to vector clocks but store a (node, counter) pair per key, not a global clock — used in Dynamo-style key-value stores. **Hybrid Logical Clocks** (HLCs) combine physical time and logical counters for systems that need both causal ordering and real-time bounds, used in CockroachDB and YugabyteDB. **Dotted version vectors** extend vector clocks with per-object dots for more efficient conflict detection in Riak.

## Complexity / Behavior Characteristics

| Operation | Time Complexity | Space Complexity |
|-----------|----------------|------------------|
| Tick | O(1) amortized | O(N) per clock |
| Merge | O(K) where K = nodes in other clock | O(N) per clock |
| Compare | O(N + M) where N, M = nodes in each clock | O(N + M) temporary |
| Clone | O(N) | O(N) per clock |

The space complexity is O(N) where N is the number of nodes in the cluster, because each node's counter must be tracked. This is the main practical limitation — in a 10,000-node cluster, every vector clock is roughly 80 KB (assuming a 4-byte integer and a 4-byte uncompressed node ID). For large clusters, interval tree clocks provide O(log N) space.

## Implementation Deep Dive

**1. Sparse representation via Go maps.** The `VectorClock` at `main.go:14` is `map[string]int`, not a fixed array. This is a deliberate choice. In a 100-node cluster, most events touch only a handful of replicas (typically 3-5 for quorum replication). A sparse map avoids storing 95+ zero entries. The comparison algorithm at `main.go:48-76` handles missing keys gracefully: `a, b := vc.clock[node], other.clock[node]` — if a key is absent from one map, it defaults to 0, which is logically correct since an un-ticked node has a count of 0.

**2. The `seen` set ensures comparison covers all nodes.** In `Compare` at `main.go:50-55`, we first build a `seen` set containing every node present in *either* clock. Then we iterate this set to compare values. If we only iterated one clock, we'd miss nodes that exist only in the other clock — a node with count 5 in clock B but absent from clock A would be incorrectly treated as equal (both 0). The seen set guarantees we evaluate every dimension of both clocks.

**3. Three-flag comparison algorithm.** The `Compare` function uses two booleans: `less` and `greater` (`main.go:49`). For each node dimension, if A's value < B's value, `less = true`; if A's value > B's, `greater = true`. After examining all nodes, the result is determined by the combination: both true = concurrent, only less = before, only greater = after, neither = equal. This is extremely efficient — a single pass with two booleans — and maps cleanly to the formal definition of the happened-before partial order.
